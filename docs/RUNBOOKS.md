# VendorFlow — Runbooks (for the owner)

Plain language on purpose. Each step says WHERE to click and WHAT to copy. Nothing here needs coding.
Design background: `adr/ADR-0010-hosting-render-supabase.md`, `DEPLOYMENT.md`.

> **Resumen en español.** Orden: (1) crear proyecto Supabase en Frankfurt, (2) crear un bucket privado y las claves S3,
> (3) crear cuenta en Render y conectar GitHub, (4) "New > Blueprint" y pegar los secretos que pide, (5) configurar el
> webhook de Stripe (live) y el dominio de Resend, (6) pasar la lista de comprobación (sección 1.9). Los secretos NUNCA se
> pegan en el chat ni en GitHub: solo en los paneles de Render, Supabase, Stripe y Resend. Si algo sale mal: secciones
> "Rollback" (3) e "Incidentes" (7).

## 1. First deploy (about 2 hours, once)

### 1.1 Accounts you need
Supabase, Render, GitHub (you have it), Stripe (live mode activated: needs your business details), Resend, and a domain name
(for sending email, and optionally for the app address).

### 1.2 Supabase (database + file storage)
1. supabase.com > New project. Name: `vendorflow-prod`. **Region: Central EU (Frankfurt)**. Set a long **database password**
   (keep it in a password manager). Plan: Pro (daily backups).
2. Project Settings > **Data API**: turn it OFF (or leave "Exposed schemas" empty). We never use it.
3. Click **Connect** > **Session pooler** (port 5432). You need: host, user (`postgres.<project-ref>`), password, database
   `postgres`. The JDBC URL is: `jdbc:postgresql://<host>:5432/postgres?sslmode=require`
4. Storage > **New bucket**: name `vendorflow-documents`, **Private** (Public OFF).
5. Storage > Settings > **S3 Connection**: copy the **Endpoint** (`https://<ref>.storage.supabase.co/storage/v1/s3`) and the
   **Region** (e.g. `eu-central-1`). Click **New access key**: copy the Access key ID and the Secret (shown once).
6. Database > Backups: check that daily backups are listed. Consider the PITR add-on (section 5).

### 1.3 Resend (email)
1. resend.com > Domains > Add domain (e.g. `mail.yourdomain.com`). Resend shows DNS records (SPF, DKIM, optionally DMARC).
   Add them at your domain provider. Wait until the domain says **Verified**.
2. API Keys > Create key, permission "Sending access", limited to that domain. Copy it.
3. `EMAIL_FROM` = `VendorFlow <notifications@mail.yourdomain.com>` (must be on the verified domain).

### 1.4 Render (hosting)
1. render.com > sign up, connect GitHub, give access to the `vendorflow` repository only.
2. **New > Blueprint** > pick the repo, branch `main`. Render reads `render.yaml` and lists 3 services
   (`vendorflow-web`, `vendorflow-api`, `vendorflow-clamav`) in **Frankfurt**.
3. It asks for the secrets (every `sync: false` variable). Fill them using the table in 1.5. For `APP_BASE_URL` use the
   Render address first (`https://vendorflow-web.onrender.com`); change it when you attach your own domain (1.7).
4. Click **Apply**. The first build takes ~10-15 minutes. ClamAV downloads its signatures on first start (a few minutes);
   until it is ready uploads are refused on purpose (fail closed).
5. Check: the `vendorflow-api` log shows `Started VendorFlowApplication` and Flyway "Successfully applied N migrations".
   `https://vendorflow-web.onrender.com/healthz` answers `ok`.

### 1.5 Environment variables: where each value comes from
| Variable (service `vendorflow-api`) | Value / where to get it |
|---|---|
| `APP_BASE_URL` | public https address of the web service (Render > vendorflow-web, or your domain) |
| `APP_IP_HASH_SECRET` | generated by Render. Nothing to do |
| `DATABASE_URL` | JDBC URL from 1.2 step 3 |
| `DATABASE_USERNAME` | `postgres.<project-ref>` (Supabase > Connect) |
| `DATABASE_PASSWORD` | the database password from 1.2 step 1 |
| `STORAGE_S3_ENDPOINT`, `STORAGE_S3_REGION` | Supabase > Storage > S3 Connection (1.2 step 5) |
| `STORAGE_S3_BUCKET` | `vendorflow-documents` |
| `STORAGE_S3_ACCESS_KEY_ID`, `STORAGE_S3_SECRET_ACCESS_KEY` | the Supabase S3 access key (1.2 step 5) |
| `RESEND_API_KEY`, `EMAIL_FROM` | Resend (1.3) |
| `STRIPE_SECRET_KEY` | Stripe (live mode) > Developers > API keys > secret key `sk_live_...` (or a restricted key `rk_live_...`) |
| `STRIPE_PRICE_ID` | Stripe (live mode) > Product catalogue > the Standard price (49 EUR / month) > `price_...`. Test-mode ids do NOT work in live mode |
| `STRIPE_WEBHOOK_SECRET` | created in 1.6 (`whsec_...`) |

Everything else (`SPRING_PROFILES_ACTIVE`, `STORAGE_PROVIDER`, `STORAGE_SCANNER`, `CLAMAV_HOST`, `EMAIL_PROVIDER`,
`BILLING_ENABLED`) is fixed in `render.yaml`. If you forget one value, the API refuses to start and its log says which
variable is missing. That is intended.

### 1.6 Stripe live webhook
1. Stripe (live mode) > Developers > Webhooks > Add endpoint.
2. URL: `https://<your-app-address>/api/v1/webhooks/stripe` (the public address of the WEB service, not of the API).
3. Events (exactly these five are used): `checkout.session.completed`, `customer.subscription.created`,
   `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed`.
4. Copy the **Signing secret** `whsec_...` into `STRIPE_WEBHOOK_SECRET` of `vendorflow-api` (Render > Environment), Save;
   the service redeploys.
5. Stripe > Settings > Billing > Customer portal: activate it (the app opens it for "manage subscription").
6. Test: in Stripe open the endpoint > "Send test event". Stripe must show HTTP 200 (or 4xx for a fake event: the point is
   that the signature is accepted and the API answers).

### 1.7 Your own domain (optional, recommended)
Render > vendorflow-web > Settings > Custom Domains > add `app.yourdomain.com`; add the DNS record Render shows. HTTPS is
automatic. Then update `APP_BASE_URL` (api) and the Stripe webhook URL.

### 1.8 Automatic deploys from GitHub (after CI passes)
1. Render > vendorflow-api > Settings > **Deploy Hook**: copy the URL. Same for vendorflow-web.
2. GitHub > repo > Settings > Secrets and variables > Actions > New repository secret: `RENDER_DEPLOY_HOOK_BACKEND` and
   `RENDER_DEPLOY_HOOK_FRONTEND` (the URLs are secrets: anyone who has one can trigger a deploy).
3. From now on every push to `main` that passes all CI jobs deploys the backend first, then the frontend. Without the
   secrets the job prints "skipped". (ClamAV needs a manual deploy only when `clamav/Dockerfile` changes.)
Alternative without GitHub secrets: in `render.yaml` set `autoDeployTrigger: checksPass` on the services (Render deploys after CI checks pass).

### 1.9 Smoke test (after the first deploy and after big releases)
- [ ] `/healthz` answers `ok`; the site opens over https.
- [ ] Sign up with a real mailbox: the verification email arrives.
- [ ] Log in, create a vendor, upload a small PDF, download it. In Supabase > Storage the file is in the bucket (not public).
- [ ] Upload the harmless EICAR test file (a text file from eicar.org): the app must REJECT it (the scanner works).
- [ ] Billing: start the trial/checkout with a real card in live mode and refund yourself, then open the customer portal.
- [ ] Do the client IP check (1.10).

### 1.10 Check the client IP (important, once)
Rate limits and audit use the visitor's IP. Behind Render's edge and the Next.js hop the API must see the visitor's address,
not Render's. Test: on your phone (mobile data) try a wrong password 11 times at the login page. Only that device must get
"too many requests"; your computer (wifi) must still be able to try. If both are blocked together, the API sees one shared IP:
tell the developer; the fix is setting `TRUSTED_PROXIES_REGEX` on `vendorflow-api` to include the extra proxy range
(SECURITY.md section 9). Do not "fix" it by trusting everything (`.*`): that lets anyone fake their IP.

## 2. Request size limits (what Render can and cannot do)
The security design wants 16 MB only on the upload route and ~1.5 MB elsewhere. Render has no per-route size setting. What is
in place instead: Next.js accepts at most 16 MB (`proxyClientMaxBodySize`), the API limits every upload (15 MB per file,
17 MB per request), and rate limits protect heavy routes. If you see abuse (large junk requests), put Cloudflare (free plan)
in front of the app domain and add a WAF rule "request body > 1.5 MB AND path is not `/api/v1/vendors/*/documents` -> block".
Details: DEPLOYMENT.md.

## 3. Rollback
- **Code (API or web):** Render > the service > Deploys > pick the last good deploy > **Rollback** (about 1 minute). Then in
  GitHub revert the bad commit (`git revert`) so the next deploy does not bring it back.
- **Database:** migrations only go forward. Because they follow expand/contract, the previous release still works against
  the new schema, so rolling code back is safe. NEVER restore the database to undo a code bug: fix forward with a new
  migration. Restore only for data loss or corruption (section 5).
- If both are bad: roll back web first, then api.

## 4. Secret rotation (at least yearly, and immediately after any suspicion)
General rule: create the new value at the provider, paste it into Render > service > Environment, Save (the service
redeploys), then revoke the old one.

| Secret | How | Side effects |
|---|---|---|
| Database password | Supabase > Database > Settings > Reset password; update `DATABASE_PASSWORD` (and `BACKUP_DATABASE_URL` on your machine) | ~1 min of errors while the API restarts |
| Stripe secret key | Stripe > Developers > API keys > Roll key (keep the old valid 1 hour); update `STRIPE_SECRET_KEY` | none if done within the hour |
| Stripe webhook secret | Stripe > the endpoint > Roll secret (keep the old valid 1 hour); update `STRIPE_WEBHOOK_SECRET` | none if done within the hour |
| Resend key | Resend > API Keys > create new; update `RESEND_API_KEY`; delete the old one | emails wait in the outbox and retry |
| Supabase S3 key | Supabase > Storage > S3 Connection > new key; update both `STORAGE_S3_*` key vars; delete the old key | uploads/downloads fail until the redeploy finishes |
| `APP_IP_HASH_SECRET` | Render > api > Environment > generate a new value | old and new audit IP hashes stop matching (acceptable); sessions are not affected |
| Sessions (log everybody out) | Sessions are stored in the database. Ask the developer, or in the Supabase SQL editor run `DELETE FROM spring_session;` | every user must log in again |
| Deploy hooks | Render > Deploy Hook > regenerate; update the GitHub secrets | none |
| Backup passphrase | create a new one; keep the old to open old backups | none |

## 5. Backups and restore drill
**What exists:** Supabase Pro keeps **daily backups for 7 days**. For recovery to any second, enable the **PITR** add-on
(Database > Backups). RPO (the most data you can lose) is 24 h without PITR and minutes with it: decide with money in mind.

**Our own copy:** `scripts/backup-db.sh` makes an encrypted dump you control (protects against problems with the Supabase
account itself).
```bash
export BACKUP_DATABASE_URL='postgresql://postgres.<ref>:<password>@<session-pooler-host>:5432/postgres'
export BACKUP_PASSPHRASE_FILE=~/.vendorflow-backup-passphrase   # a file holding a long random passphrase (chmod 600)
scripts/backup-db.sh ~/vendorflow-backups
```
Needs `pg_dump` 17 and `gpg` (Windows: Git Bash + PostgreSQL 17 client + Gpg4win). Run it weekly and copy the file to a second
place. It is encrypted, but still do not email it.

**Storage (the documents):** Supabase does NOT back up the Storage files together with the database. Copy the bucket
regularly with any S3 tool, e.g. `rclone sync supabase:vendorflow-documents ~/vendorflow-docs-backup` (rclone remote: type
s3, provider Other, path-style on, the endpoint/keys from 1.2). Metadata is in the database, the bytes are in the bucket:
restore both or neither.

**Restore drill (do it once now, then every quarter), never on production:**
1. Throwaway Postgres: `docker run -d --name restore-test -e POSTGRES_PASSWORD=x -p 55432:5432 postgres:17-alpine`
2. `gpg --batch --decrypt --passphrase-file ~/.vendorflow-backup-passphrase vendorflow-<stamp>.sql.gz.gpg | gunzip | psql postgresql://postgres:x@localhost:55432/postgres`
3. Check: `select count(*) from organization;` and `select max(installed_rank) from flyway_schema_history;` look right.
4. Optional: start the API locally against it (`DATABASE_URL=jdbc:postgresql://localhost:55432/postgres`, user `postgres`, password `x`) and log in.
5. `docker rm -f restore-test`. Write the date and how long it took in `docs/SESSION_HANDOFF.md`.

**Real restore on Supabase:** Dashboard > Database > Backups > Restore (replaces the data). First suspend the API (Render >
vendorflow-api > Suspend), restore, resume, run the smoke test (1.9).

## 6. Monitoring and alerts
- **Logs:** every service writes to stdout; Render > service > Logs. The API logs one JSON line per event (ECS format, with a
  request id). Passwords, tokens and document contents are never logged.
- **Health:** `/healthz` (web) and `/actuator/health/liveness|readiness` (api, private). Render restarts a service that fails
  its health check.
- **Uptime check (free, recommended):** UptimeRobot or Better Stack, HTTPS monitor on `https://<app>/healthz` every 5 minutes,
  alert by email/SMS. It tests the public path only; backend problems are caught by the log alerts below.
- **Log-based alerts:** Render > Settings > Log Streams sends logs to a log service (Better Stack, Datadog, Papertrail).
  Create alerts on these exact texts:

| Search for | Meaning | Action |
|---|---|---|
| `Stripe event processing failed` | a billing webhook could not be applied | after the fix, Stripe > Webhooks > resend the event |
| `Stripe webhook rejected` (many in a row) | wrong `STRIPE_WEBHOOK_SECRET`, or someone probing | check the secret |
| `Notification permanently failed` / `status=DEAD` | an email will never be delivered | check Resend (domain, key, quota) |
| `File scanner unavailable` | ClamAV is down or still starting: all uploads are refused | Render > vendorflow-clamav status and logs |
| `Chasing vendor failed` (or the counter `vendorflow.chasing.vendor.failures` > 0) | automated chasing skipped a vendor because processing it threw; the line carries `organizationId`, `vendorId` and the exception class only; the other vendors were chased and the next hourly tick retries it | find the vendor, fix its data or the bug; repeated for the same vendor = a poison record |
| `Automated chasing is enabled but vendorflow.mail.postal-address is not configured` | chasing is on for an organization but no chase is sent (CAN-SPAM postal address missing); logged once per process | set `VENDORFLOW_MAIL_POSTAL_ADDRESS` and redeploy |
| `Chasing daily cap reached` | an organization hit `app.chasing.max-per-org-per-day` (200); the rest goes the next day | normal for big lists; raise the cap only deliberately |
| `Outbox dispatch failed` | the email job crashes | ask the developer, include the log line |
| `"log.level":"ERROR"` | anything unexpected | read the context |
| `FILESYSTEM STORAGE IN PROD`, `BILLING IS DISABLED IN PROD` | an unsafe opt-in is active | remove the opt-in |

- **Future (needs an ADR first):** Sentry for exceptions, a metrics dashboard.

## 7. Incident basics
1. **Us or a provider?** Check status.render.com, status.supabase.com, status.stripe.com and Resend's status page. If a provider
   is down: wait; tell customers if it lasts more than 30 minutes.
2. **Site down:** Render > service > Events: a failed deploy? Roll back (section 3). Health check failing? Read the Logs.
3. **API will not start:** the last log lines say why. Usual causes: a missing or wrong variable (the message names it), the
   Supabase password changed, a failed migration (fix with a NEW migration; never edit an old one, never "repair" blindly).
4. **Uploads fail:** `File scanner unavailable` means ClamAV; storage errors mean Supabase Storage status or a rotated S3 key.
5. **Emails do not arrive:** Resend dashboard (domain verified? quota?). Rows wait in the outbox and retry.
6. **Suspected breach or leaked secret:** rotate that secret NOW (section 4), log every user out, look at the `audit_event`
   table, write down times, tell the developer. Notify affected customers as the law requires (US state breach laws: ask a lawyer).
7. **Data loss:** suspend the API, restore (section 5), resume, verify, write the post-mortem in `docs/SESSION_HANDOFF.md`.

After any incident: write what happened, why, and the fix; add a test or an alert so it cannot repeat silently.
