# VendorFlow — Database Design

> Flyway owns the schema (`backend/src/main/resources/db/migration`). Hibernate runs with `ddl-auto=validate`.
> Never edit an applied migration; add a new one. Never change production by hand.

## 1. Conventions
- PostgreSQL 17. Table names singular snake_case. PKs: `id uuid` generated by the application.
- Timestamps: `timestamptz`, UTC. Business dates (issue/expiration): `date` (no time zone — a COI expires on a
  calendar day). "Today" for compliance is evaluated in the **organization's time zone**.
- Enums stored as `text` + `CHECK` constraint (easier to evolve than Postgres enums; mapped with `@Enumerated(STRING)`).
- Every tenant-owned table has `organization_id uuid NOT NULL` and a `UNIQUE (organization_id, id)` so children can
  reference it with a **composite foreign key** — a row can never point at a parent in another tenant.
- `ON DELETE` is `RESTRICT` by default. We soft-delete/archive business data; hard deletes are explicit operations.
- Case-insensitive emails via `lower(email)` unique indexes (no `citext` extension needed → Supabase-portable).

## 2. Entity overview

```
organization 1─* membership *─1 app_user
organization 1─* invitation
organization 1─* vendor 1─* vendor_requirement *─1 document_type *─1 organization
                 vendor 1─* document *─1 document_type
                            document 1─* reminder
organization 1─* notification          (email outbox)
organization 1─1 subscription
organization 1─* audit_event
stripe_event                            (global, webhook idempotency)
app_user 1─* user_token                 (email verification / password reset)
spring_session, spring_session_attributes (managed by Spring Session JDBC)
```

## 3. Tables

### organization
| column | type | notes |
|---|---|---|
| id | uuid PK | |
| name | text NOT NULL | 1–120 chars |
| time_zone | text NOT NULL default 'America/New_York' | IANA zone; used to compute "today" |
| expiring_window_days | int NOT NULL default 30 | doc is EXPIRING when ≤ N days left; CHECK 1..180 |
| reminder_offsets_days | int[] NOT NULL default '{30,14,7,1}' | reminder thresholds before expiry |
| reminders_enabled | boolean NOT NULL default true | |
| created_at / updated_at | timestamptz | |

### app_user (`user` is reserved in Postgres)
| column | type | notes |
|---|---|---|
| id | uuid PK | |
| email | text NOT NULL | unique index on `lower(email)` |
| full_name | text NOT NULL | |
| password_hash | text NOT NULL | Spring `DelegatingPasswordEncoder` (`{bcrypt}`, cost 12) — upgradeable in place; see ADR-0002 |
| email_verified_at | timestamptz NULL | |
| failed_login_attempts | int NOT NULL default 0 | brute-force lockout |
| locked_until | timestamptz NULL | |
| last_active_organization_id | uuid NULL FK organization ON DELETE SET NULL | restores the active org at login; always re-verified against membership |
| last_login_at, created_at, updated_at | timestamptz | |

Users are global (one person can belong to several organizations).

### membership
`id, organization_id FK, user_id FK, role text CHECK IN ('OWNER','ADMIN','MEMBER','VIEWER'), created_at, updated_at`
- `UNIQUE (organization_id, user_id)`; index `(user_id)`.
- Invariant (service-enforced, tested): an organization always has ≥ 1 OWNER.
- Roles are a fixed enum, not a table — permissions are code (`RolePermissions`), reviewed in PRs. ADR-0008.

### invitation
`id, organization_id, email, role (not OWNER), token_hash (SHA-256 of random 256-bit token), invited_by_user_id,
expires_at, accepted_at, revoked_at, created_at`
- Partial unique index: one pending invitation per `(organization_id, lower(email))` where `accepted_at IS NULL AND revoked_at IS NULL`.
- Raw token only exists in the email link; DB stores the hash.

### user_token
`id, user_id FK, purpose CHECK IN ('EMAIL_VERIFICATION','PASSWORD_RESET'), token_hash UNIQUE, expires_at, used_at, created_at`

### vendor
| column | type | notes |
|---|---|---|
| id | uuid PK | |
| organization_id | uuid NOT NULL FK | |
| company_name | text NOT NULL | unique per org on `lower(company_name)` (also the CSV upsert key) |
| contact_name, email, phone | text NULL | email format validated in API |
| category | text NULL | free text in MVP (e.g. "Plumbing"); becomes ruleset input later |
| status | text NOT NULL default 'ACTIVE' | `ACTIVE | INACTIVE`; inactive vendors are excluded from compliance counts and reminders |
| notes | text NULL | ≤ 5000 chars |
| created_by_user_id | uuid NULL FK app_user | |
| created_at / updated_at | timestamptz | |
Indexes: `UNIQUE (organization_id, id)`, `UNIQUE (organization_id, lower(company_name))`, `(organization_id, status)`.

### document_type
`id, organization_id, code, name, has_expiration bool, required_by_default bool, active bool, sort_order, created_at, updated_at`
- Seeded **per organization** at org creation (COI, GENERAL_LIABILITY, WORKERS_COMP, BUSINESS_LICENSE,
  PROFESSIONAL_LICENSE, W9, CONTRACT, OTHER) so each org can rename/deactivate/add types.
- `UNIQUE (organization_id, code)`, `UNIQUE (organization_id, id)`.
- W-9 and Contract default `has_expiration=false`.

### vendor_requirement
`id, organization_id, vendor_id, document_type_id, created_at`
- `UNIQUE (vendor_id, document_type_id)`.
- Composite FKs: `(organization_id, vendor_id) → vendor`, `(organization_id, document_type_id) → document_type`.
- On vendor creation, rows are materialized from `document_type.required_by_default`. The user can then add/remove
  requirements per vendor. Future: rulesets by vendor category generate these rows (no schema change needed).

### document
One uploaded file + its compliance metadata. History = chain of superseded documents + audit events.
| column | type | notes |
|---|---|---|
| id | uuid PK | |
| organization_id | uuid NOT NULL | |
| vendor_id | uuid NOT NULL | composite FK → vendor |
| document_type_id | uuid NOT NULL | composite FK → document_type |
| state | text NOT NULL | `CURRENT | SUPERSEDED | ARCHIVED` |
| review_status | text NOT NULL | `PENDING | APPROVED | REJECTED` |
| issue_date | date NULL | |
| expiration_date | date NULL | required when type `has_expiration` (service-validated; type can change) |
| storage_key | text NOT NULL | server-generated, never derived from user input |
| original_filename | text NOT NULL | sanitized, display-only, ≤ 255 chars |
| mime_type | text NOT NULL | **detected from magic bytes**, not the client header |
| size_bytes | bigint NOT NULL | CHECK > 0 |
| sha256 | text NOT NULL | integrity + future duplicate detection |
| uploaded_by_user_id | uuid NULL FK | NULL reserved for future vendor-portal uploads |
| superseded_by_document_id | uuid NULL | |
| reviewed_by_user_id, reviewed_at, review_note | | |
| created_at / updated_at | timestamptz | |
Indexes:
- **Partial unique** `(vendor_id, document_type_id) WHERE state = 'CURRENT'` → at most one current doc per requirement.
- `(organization_id, expiration_date) WHERE state = 'CURRENT'` → dashboard + reminder scans.
- `(organization_id, vendor_id)`.

Uploading a new document for a (vendor, type) that already has a CURRENT one marks the old one SUPERSEDED in the
same transaction. Nothing is overwritten. Metadata edits (dates, review) emit audit events with before/after values.

### reminder (idempotency ledger)
`id, organization_id, document_id, kind CHECK IN ('EXPIRING','EXPIRED'), offset_days int, expiration_date date, notification_id uuid NULL, created_at`
- `UNIQUE (document_id, kind, offset_days, expiration_date)` — a given threshold for a given expiration fires once,
  no matter how many times or on how many instances the job runs. If the expiration date changes (renewal/edit),
  new thresholds apply naturally.
- MISSING-document reminders are part of the daily digest content, not a per-row ledger (they have no threshold).

### notification (transactional outbox)
| column | type | notes |
|---|---|---|
| id | uuid PK | |
| organization_id | uuid NULL | NULL for account emails (verification/reset) |
| kind | text | `INVITATION, EMAIL_VERIFICATION, PASSWORD_RESET, COMPLIANCE_DIGEST, DOCUMENT_REQUEST` |
| recipient_email | text NOT NULL | |
| idempotency_key | text NOT NULL UNIQUE | e.g. `digest:{org}:{user}:{2026-10-03}` |
| payload | jsonb NOT NULL | minimal template data — **never raw tokens**; links are built at send time from a token reference where possible |
| status | text | `PENDING, SENDING, SENT, FAILED, DEAD` |
| attempts | int, next_attempt_at timestamptz, last_error text (sanitized, truncated) | |
| provider_message_id | text NULL | Resend id |
| sent_at, created_at, updated_at | timestamptz | |
Index: `(status, next_attempt_at)`.

> Note on tokens in payload: verification/reset/invite emails need the raw token in the link. The raw token is stored
> in the payload only until the email is SENT (or DEAD); the dispatcher then removes the secret field from the payload.

### spring_session / spring_session_attributes
Created by our own Flyway migration (copied from Spring Session JDBC's PostgreSQL schema), with
`spring.session.jdbc.initialize-schema=never` so Flyway remains the single owner of the schema.
The session principal name is the **user id** (not the email), so all sessions of a user can be found and deleted
(password reset, account lock).

### subscription
`id, organization_id UNIQUE, status CHECK IN ('TRIALING','ACTIVE','PAST_DUE','CANCELED','INCOMPLETE','UNPAID'),
plan text, stripe_customer_id UNIQUE NULL, stripe_subscription_id UNIQUE NULL, trial_ends_at, current_period_end,
cancel_at_period_end bool, updated_at, created_at`
- Created as TRIALING at org creation. Only the Stripe webhook handler changes Stripe-derived fields.

### stripe_event
`id text PK (Stripe event id), type text, stripe_created_at timestamptz, received_at, processed_at, status ('PROCESSED','FAILED'), error text`
- Insert-first idempotency: a duplicate delivery hits the PK and is acknowledged without reprocessing.

### audit_event (append-only)
`id, organization_id NULL, actor_user_id NULL, action text (e.g. 'document.uploaded'), entity_type, entity_id uuid,
metadata jsonb (before/after for changed fields; no secrets, no document contents), request_id, ip_hash, created_at`
- Index `(organization_id, entity_type, entity_id, created_at desc)` and `(organization_id, created_at desc)`.
- No UPDATE/DELETE from application code. Retention: see SECURITY.md §Privacy.

## 4. Migration strategy
- Flyway versioned migrations `V{n}__{description}.sql`, forward-only. Repeatable seed data is **not** used for
  production (document types are seeded per org by application code at org creation).
- Every migration is exercised by the Testcontainers integration test suite on each CI run.
- Destructive changes use expand → migrate → contract across separate releases.

## 5. Query rules
- Every repository method for a tenant-owned table includes `organizationId`.
- All list endpoints are paginated (default 25, max 100) with an index-backed sort.
- Vendor list with compliance summary is a single aggregate query (no per-vendor queries).

## 6. Implementation notes (V2, Phase 1 B1)
- `V2__identity_organizations.sql` creates organization, app_user, membership, invitation, user_token, audit_event,
  notification and the Spring Session tables (copied from `spring-session-jdbc` 4.1.1 `schema-postgresql.sql`).
- Extra CHECKs beyond the tables above: organization name 1–120 chars and `reminder_offsets_days` 1–5 elements each 1–180;
  `app_user.full_name` 1–100, `email` ≤ 254; `invitation.role` ∈ ADMIN/MEMBER/VIEWER; `notification.kind` ∈ the listed kinds.
- `invitation.token_hash`, `user_token.token_hash` and `notification.idempotency_key` are `UNIQUE`.
- `audit_event.organization_id` / `actor_user_id` are FKs with NO `ON DELETE` action (RESTRICT): audit rows are never
  rewritten or cascaded away; deleting an org/user is blocked until a retention policy exists.
- `notification` also has `UNIQUE (organization_id, id)` (tenant-table convention, organization may be NULL).
- Composite FKs `(organization_id, x_id)` are not used yet in V2: no tenant child table exists until Phase 2 (vendor).
